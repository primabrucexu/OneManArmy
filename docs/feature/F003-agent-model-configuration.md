# F003 Agent 模型配置

**STATUS**：已实现并验证
**MileStone**：第一阶段

## What

### 目标

在设置页面提供 Agent 模型配置入口，使用户可以按项目微调四个固定 Agent 的模型与推理等级，同时保证同一需求中的 Agent 配置稳定、可追溯，不在执行过程中切换模型。

本需求只配置 OneManArmy 已确定的四个角色，不将产品扩展为通用 Agent 平台或动态模型路由系统。

### Agent 角色与推荐默认值

每个项目包含以下四个固定 Agent 配置：

| Agent | 职责 | 推荐默认模型 | 推荐推理等级 |
| --- | --- | --- | --- |
| 需求 Agent | 需求讨论并维护需求文档 | `gpt-5.6-terra` | `medium` |
| 计划 Agent | 根据已确认需求文档制定实施方案并维护 `How` | `gpt-6-astra` | `high` |
| 编码 Agent | 根据需求文档和 `How` 编码、测试并修正问题 | `gpt-5.6-sol` | `high` |
| 审核 Agent | 独立执行各阶段审核和最终整体验收 | `gpt-6-astra` | `high` |

审核 Agent 在同一需求中始终使用同一模型和推理等级，不在最终整体验收时临时提高或更换配置。

### 设置入口

- 侧栏“设置”继续作为配置入口。
- 设置页面新增“Agent 配置”区域。
- 页面为四个固定 Agent 分别展示角色名称、职责、模型和推理等级。
- 每个 Agent 只允许修改模型和推理等级。
- 页面提供“保存配置”和“恢复推荐默认值”操作。
- “恢复推荐默认值”只修改当前编辑值，用户保存后才正式生效。
- 模型选项只展示当前运行环境可用的 Codex 模型。
- 推理等级选项必须与所选模型实际支持的等级一致；不支持的组合不得保存。
- 保存成功或失败必须提供明确反馈，不得把未持久化的修改显示为已生效。

### 配置作用域与版本

- Agent 配置是项目级默认配置，不是全局共享配置。
- 当前版本只有默认项目时，设置页面编辑该默认项目的配置。
- 每次成功保存实际发生变化的配置后，生成新的配置版本。
- 页面展示当前已保存的配置版本和更新时间。
- 不提供单个需求的临时覆盖配置。

### 需求配置快照

- 用户为新需求发送第一条有效消息、需求被正式创建时，系统复制当时项目中四个 Agent 的完整配置，形成该需求的配置快照。
- 配置快照至少包含配置版本、四个 Agent 的模型和推理等级。
- 同一需求从需求讨论到最终交付始终使用该快照。
- 项目设置后续发生变化时，只影响之后创建的新需求，不影响已经创建、正在执行、暂停或已经完成的需求。
- 在本需求上线前已经存在的需求继续使用其原有执行配置，不因用户保存新配置而切换模型。
- 需求详情页只读展示该需求实际使用的四个 Agent 配置和配置版本。
- Agent 运行记录必须保留实际模型和推理等级，以便追踪交付结果。

### 配置稳定性

- Agent 创建后，其模型和推理等级不得在同一需求执行过程中修改。
- 审核退回、测试失败或自动修正时，由原 Agent 使用原配置继续处理。
- 配置不足不能通过静默切换模型解决；系统应保留当前状态并按照工作流的失败处理规则继续处理或请求用户决策。
- 用户修改项目配置时，页面必须明确提示“修改仅影响之后创建的需求”。

### 与现有需求的关系

- F001 继续定义工作台、需求讨论界面和设置入口；F003 将其中只读设置视图扩展为包含可编辑的 Agent 配置。
- F003 只替代 F001 中“不提供可编辑配置”和“不新增模型选择”的限制，不改变 F001 的其他界面与需求讨论规则。
- F002 继续负责历史需求对话及其本地持久化；F003 为每个新需求增加不可变的 Agent 配置快照。
- 三阶段工作流、各阶段 Agent 的具体执行以及独立审核业务不在本需求中实现；本需求只建立其配置入口和配置快照边界。

### 非目标

- 不允许新增、删除或重命名 Agent 角色。
- 不开放 Agent 提示词、工具、文件权限、沙盒权限或重试次数配置。
- 不实现动态模型路由、自动模型升级、执行中模型切换或按步骤选择模型。
- 不提供单个需求或单次运行的临时模型覆盖。
- 不提供配置效果统计、模型对比实验或成本分析页面。
- 不建设通用 Agent 市场或第三方模型供应商抽象。
- 不在本需求中实现计划阶段、编码阶段、审核 Agent 或完整三阶段工作流。

## How

### 状态与兼容

- 在现有项目状态中保存项目级 Agent 配置、配置版本和更新时间；新需求在第一条有效消息写入时原子复制完整配置快照。
- 状态格式升级时兼容 F002 已有数据。旧需求不补写无法证明的模型信息，并在续接原 Codex Thread 时继续不传模型覆盖。
- 配置实际发生变化时才递增版本；项目后续配置变化不得修改已有需求快照。

### 模型目录与接口

- 保留现有 Codex SDK 执行链，使用一次性 stdio Codex App Server 的 `model/list` 获取当前可用模型和各模型支持的推理等级，不维护硬编码可选列表。
- 新增模型目录读取、项目 Agent 配置读取和项目 Agent 配置保存接口。
- 服务端保存前根据最新模型目录校验四个固定角色及其模型、推理等级组合；读取模型目录失败时明确返回错误，不静默使用过期或伪造列表。

### Agent 执行配置

- 需求讨论从需求配置快照读取需求 Agent 的模型和推理等级，并在首次创建和后续恢复 Thread 时始终传入相同配置。
- F003 只保存计划、编码和审核 Agent 的配置，不提前实现尚未进入范围的阶段执行。

### 页面

- 将现有设置页扩展为四个固定 Agent 的配置表单，提供模型、推理等级、配置版本、更新时间、保存状态和恢复推荐默认值。
- 模型变化时只展示该模型实际支持的推理等级；目录或保存失败时展示真实错误并禁止伪保存。
- 在需求详情页展示该需求的只读配置快照；旧需求明确显示创建时配置未记录。

### 验证

- 覆盖旧状态兼容、项目隔离、配置版本、无变化保存、需求快照冻结、非法模型组合、模型目录协议解析和 Codex Thread 参数传递测试。
- 运行 `npm test`、`npm run build`，并在真实浏览器中验证设置交互、刷新恢复和需求快照展示。

## MCP

本需求不新增 MCP Tool。

## Acceptance Criteria

1. 用户可以从侧栏“设置”进入 Agent 配置区域。
2. 设置页面固定展示需求、计划、编码和审核四个 Agent，不能新增、删除或重命名角色。
3. 用户可以分别选择四个 Agent 的模型和推理等级。
4. 页面只允许保存当前运行环境支持的模型与推理等级组合。
5. 用户可以将编辑值恢复为本需求定义的推荐默认配置，并在保存后生效。
6. 配置按项目隔离，保存一个项目的配置不会修改其他项目的配置。
7. 实际发生变化的配置保存成功后产生新的配置版本，并展示版本和更新时间。
8. 新需求发送第一条有效消息并正式创建时，保存当时四个 Agent 的完整配置快照。
9. 项目配置修改后，已经创建的需求及其四个 Agent 配置保持不变，只有之后创建的新需求使用新配置。
10. 同一需求执行过程中，任何 Agent 都不会因项目配置变化而切换模型或推理等级。
11. 需求详情页只读展示该需求实际使用的配置版本、四个 Agent 的模型和推理等级。
12. 保存失败时页面明确显示失败状态，刷新后仍以最后一次成功保存的配置为准。
13. 页面明确说明配置修改只影响之后创建的需求。
14. 页面不提供提示词、工具、权限、重试次数、动态路由或执行中模型切换配置。
