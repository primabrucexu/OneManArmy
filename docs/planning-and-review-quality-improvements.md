# 规划与审核质量改进

状态：已在仓库源代码中实现。

## 背景

一次真实 OMA 运行连续经历两轮计划审核退回。复盘发现，上游 Plan 的方案质量和下游 Review 的范围控制都存在问题：

- Discuss 只冻结了目标和验收要求，没有把关键平台能力、候选技术路径及排除结论作为正式输入交给 Plan。
- Plan 缺少提交前的完整性与一致性校验，可能产生执行顺序矛盾、未经验证的能力假设，或者用人工操作替代已确认的自动行为。
- Plan 收到审核意见后倾向于局部修补，没有重新检查完整方案，容易由修补引入新的绑定、并发和恢复问题。
- Review 没有强制绑定冻结需求或项目约束，可能按照“理想系统”提出额外兼容、迁移、扩展或优化要求。
- 后续 Reviewer 看不到上一轮阻塞意见，审查范围可能在每轮返工中继续扩大。

本次改进的目标是提高方案与审核质量，同时保持 OMA 流程简单。

## 总体原则

流程仍然保持：

```text
Discuss → Plan → Review → Code → Review
```

不新增可行性 Agent、自检 Agent、优化建议阶段或新的工作流循环。改进内容全部融入现有 Skill 的职责以及 Runner 已有的阶段交接。

## Discuss：初步实现设想与可行性验证

Discuss 除了确认用户目标、范围、排除项和验收标准，还需要形成足以支撑可行性判断的初步技术设想。

初步技术设想只需说明：

- 大致涉及哪些系统或组件；
- 依赖哪些现有能力和权限；
- 关键数据或状态如何流转；
- 存在哪些候选实现路径；
- 每条候选路径的关键限制。

它停留在技术路径层面，不展开到具体文件、类、函数、数据结构和实施步骤；这些内容仍由 Plan 负责。

在需求最终确认和冻结前，Discuss 对阻塞性交付条件进行验证：

- 必需的平台或宿主能力是否真实存在；
- 当前权限、沙箱和 Git 边界是否允许；
- 需求之间是否存在硬冲突；
- 候选技术路径是否能够实现目标；
- 是否仍存在无法验证的关键假设。

可行性验证不能只得出“可行”或“不可行”。如果存在 A、B、C 三条候选路径，而验证结果是只有 C 可行，冻结输入必须记录：

```text
A：排除，包含原因和证据
B：排除，包含原因和证据
C：已验证可行，作为本次实施路径
```

无法解决的关键问题应作为 Discuss 的确认项交给用户，不得带着阻塞性假设进入 Plan。

## 冻结可行性约束

已确认的可行性结论不能只存在于聊天历史中。冻结需求输入需要包含简洁的“初步实现设想与可行性约束”，至少记录：

- 已确认的可行路径；
- 已排除的路径及原因；
- 必须遵守的平台、权限和环境约束；
- 仍然成立的关键假设。

这些内容和需求一起成为 Plan 与 Review 的正式依据，不另建新的 Agent 或流程阶段。

## Plan：沿已确认路径制定方案

Plan 必须遵守冻结的可行性约束，不得：

- 重新采用 Discuss 已排除的方案；
- 将已验证方案替换成未经验证的方案；
- 降低、改变或扩大冻结需求；
- 将已确认的自动行为改成人工操作；
- 自行增加新的技术范围。

如果只有 C 可行，Plan 必须基于 C 制定具体实施方案。如果 Plan 发现 C 实际不可行，或者必须改用新的 D，应该返回失败并交回 Discuss 完成验证和确认，不能静默切换路径。

### 提交前校验

不新增自检 Agent。Plan 在同一次调用中、返回 `completed` 前完成以下校验：

- 每条验收标准都有对应的实施步骤；
- 每条验收标准都有明确的验证方法；
- 方案遵守冻结的可行路径和项目约束；
- 方案没有改变、降低或扩大需求；
- 执行顺序不存在内部矛盾；
- 不存在未经验证的关键能力假设。

收到 Review 反馈后，Plan 可以修正相应问题，但再次提交前必须重新检查完整方案，不能只验证局部补丁。

## Review：封闭审查范围

Reviewer 的审查依据只允许来自：

- 冻结需求；
- 已确认的可行性约束；
- 验收标准；
- 项目已有强制约束。

每个阻塞项必须说明：

```text
依据：违反的需求、可行性约束、验收标准或项目约束
缺陷：当前方案或实现哪里不满足
要求：最终必须达到什么结果
```

无法引用明确依据的问题不得输出，也不得影响审核结果。

Reviewer 只指出必须满足的结果，不替 Plan 指定锁、队列、UUID、迁移算法等具体实现。例如：

```text
允许：并发创建两个 OMA 时不能因为正常资源竞争导致其中一个失败。
不允许：必须使用有界锁和全局 UUID 实现并发控制。
```

## 禁止非必要优化建议

Reviewer 只输出会阻止当前需求正确验收的问题，不输出：

- 可选优化或未来建议；
- 顺手重构；
- 未经要求的旧版本迁移；
- 额外兼容性或扩展能力；
- 不影响当前验收的架构偏好；
- 仅仅因为存在“更好方案”而产生的修改要求。

审核结果保持三种：

```text
completed：当前方案或实现满足全部冻结要求。
revise：存在有明确依据、且无需改变冻结需求的可修正缺陷。
failed：必须修改需求、改变可行性路径，或者当前环境客观无法实现。
```

`failed` 应停止当前自动规划或实现，并返回 Discuss，不允许通过继续返工来扩大冻结需求。

## 限制多轮审核扩张

后续 Reviewer 需要收到上一轮阻塞反馈，但不需要建立复杂的 issue 系统：

- 优先检查上一轮问题是否已经解决；
- 检查本轮修订是否引入新的缺陷；
- 新增阻塞项仍然必须引用冻结依据；
- 上一轮已经存在但漏检的问题，应明确标记为“上轮漏检”；
- 不得把新的优化想法升级成阻塞项；
- 第一轮审核应一次性返回当前能够识别的全部阻塞问题。

Runner 只需保存并把上一轮审核反馈传给下一次 Reviewer。

## 职责边界

| 阶段 | 职责 |
| --- | --- |
| Discuss | 明确需求，形成初步技术候选，验证可行路径，冻结路径约束 |
| Plan | 沿已确认路径制定具体方案，并在同一次调用中完成提交前校验 |
| Review | 只判断方案是否满足冻结需求、可行性约束和项目强制约束 |
| Code | 按已审核方案实施 |
| Code Review | 只判断实现是否符合冻结需求和已审核方案 |

## 验收标准

1. Discuss 判断 A、B 不可行、C 可行后，Plan 不会重新采用 A 或 B。
2. Plan 发现 C 不可行时停止并返回 Discuss，不会自行选择未经验证的 D。
3. Plan 的每条验收标准都有实施步骤和验证方法。
4. Plan 修订审核问题后会重新检查完整方案，而不是只校验局部补丁。
5. Reviewer 无法引用冻结需求、可行性约束、验收标准或项目强制约束时，不能返回 `revise`。
6. 未要求的旧版本迁移、额外兼容性和未来优化不能成为阻塞项。
7. Reviewer 只描述必须满足的结果，不替 Plan 指定具体实现。
8. 第二轮及后续 Reviewer 能看到上一轮反馈，不会无依据扩大审核范围。
9. 整个改进不增加新的 Agent 或工作流阶段。

## 本次不包含

此前诊断出的以下 Runner 可靠性问题不属于本次流程质量改进：

- 缺少整个 OMA run 的总时间限制；
- 当前 30 分钟只限制单个自主阶段；
- 外层任务持续前台轮询；
- 用户中断后 `state.json` 可能残留虚假的 `running` 状态。

这些问题需要单独讨论是否纳入后续改进。
