# Plan 前的交付清单最终确认

状态：用户已确认，已在仓库 Skill 指令和 README 中实施。

## 目标与理解

OMA 在制定计划前，必须先向用户明确输出本次需要交付的成果，并等待用户对这份清单做最终确认。

这里的“交付”指用户最终得到的功能、行为、文档或其他成果，以及判断是否完成的验收标准。文件、类、函数和具体实施步骤仍由 Plan 决定。

## 当前依据

- oma-discuss 已要求批量收集确认项、展示正式需求提案、等待明确确认并冻结需求。
- oma-delivery 在需求确认后启动 Runner，进入 Plan。
- 现有指令未明确要求最终确认前展示一份完整的交付清单。
- discuss.mjs 已支持保存完整助手回复、当前草稿和最终确认记录，可直接承载清单与用户回复。

## 建议行为

保持 Discuss → Plan → Review → Code → Review，把以下要求纳入 Discuss 结束时的现有最终确认：

1. 汇总并展示“本次交付清单”，按成果编号。每项说明交付什么、用户可以观察到什么行为或结果、对应验收标准。
2. 同时列出明确排除的范围，以及尚未解决、会影响交付的事项。存在未解决的实质确认项时继续讨论。
3. 将展示的清单保存到当前草稿和讨论日志。正式需求输入必须能逐项对应确认后的清单。
4. 用户针对当前清单明确表示最终确认后，才能冻结需求并启动 Plan。逐项回答或“全部按推荐”仅用于解决讨论中的确认项；只有回复明确包含对已展示清单的最终执行确认时，才可以同时完成最终确认。
5. 清单在确认前发生变化时，重新展示完整清单并取得最终确认。恢复未确认讨论时读取保存记录，确认不能依赖聊天记忆。
6. 已有正式需求文件也必须先展示交付清单。内容完整时继续直接引用原文件；有已确认缺口时沿用现有补充文件机制。
7. Plan 基于冻结成果和验收标准制定实施步骤与验证方法。

建议展示格式：

| 编号 | 交付成果 | 用户可见行为或结果 | 验收标准 |
| --- | --- | --- | --- |
| D1 | 根据已讨论需求填写 | 可观察、可验证的结果 | 明确的完成条件 |

清单后展示已排除范围和未决事项，再请用户明确最终确认当前完整清单。
